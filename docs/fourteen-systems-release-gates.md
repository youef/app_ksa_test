# مراجعة إصدار الأنظمة الأربعة عشر

هذه وثيقة تجهيز ومراجعة وليست إثباتًا لنسخة احتياطية أو إذنًا بتنفيذ SQL. ترحيل السوق المستقل المنشور منفصل عن ترحيل الأنظمة الأربعة عشر الذي رفضته المراجعة الآلية بسبب اتساع تغييرات الصلاحيات وعدم إثبات الاستعادة.

## النسخة التي تخضع للمراجعة

الملفات `artifacts/integration-rbac.sql` و`integration-commerce.sql` و`integration-community.sql` و`integration-analytics.sql` و`integration-rbac-extra.sql` مرشحات محلية. تُثبت بصماتها في `artifacts/fourteen-systems-review-manifest.json` قبل مراجعتها. أي تغيير فيها يلغي نتائج اعتماد النص السابق. لا تُرفع لقائمة migrations الإنتاجية تلقائيًا.

## ما تم التحقق منه وما لم يتم

- تحقق اتصال المشروع وحالته الصحية. الخطة الحالية Free؛ لا توجد بيئة Supabase فرعية متاحة ضمن هذه الخطة في المحاولة السابقة.
- الاختبارات المعزولة تستخدم PostgreSQL عبر PGlite وبيانات مصطنعة داخل الاختبار فقط؛ لا تثبت وصول الإشعارات الحقيقية أو Cron أو Auth أو Storage أو نجاح استعادة إنتاجية.
- أدوات الاتصال الحالية لا تقدم تنزيل نسخة احتياطية. لم تُنزّل بيانات مستخدمين، ولم تُنشأ نسخة احتياطية أو تُجرّب استعادتها.
- لا تتوفر في الجهاز أدوات `pg_dump` أو Android adb أو Java عبر PATH وقت الفحص. تصدير حزم JavaScript للهاتف يختلف عن بناء APK/IPA وتجربته على أجهزة.

## بوابات التنفيذ

1. توفير اتصال قاعدة بيانات مصرح وآمن وأداة نسخ، ومكان مشفر خارج Git لحفظ نسخة كاملة متسقة. لا تُرسل كلمات المرور أو المفاتيح عبر المحادثة.
2. نسخ قاعدة البيانات بما يشمل Auth والسياسات والدوال والقيود، ونسخ ملفات Storage مستقلة؛ توثيق الوقت والبصمة والتشفير والاحتفاظ. نسخة المخطط المحلي لا تكفي.
3. استعادة النسخة إلى مشروع معزول، مع تعطيل إرسال الإشعارات والمدفوعات للخارج. مطابقة أعداد الصفوف والعلاقات وعينات الملفات وتسجيل زمن الاستعادة.
4. تطبيق النص ذي البصمة المعتمدة كاملًا في البيئة المعزولة، واختبار كل نظام بحساب عادي ومالك ومدير وحساب غير مصرح، وتسجيل نتائج Auth وRealtime وStorage وCron والإشعارات.
5. مراجعة السياسات المحذوفة والبديلة ودوال SECURITY DEFINER ومنح TRUNCATE وعمود totp_secret وتصعيد الصلاحيات، والتأكد من عدم فقد سياسة يعتمد عليها التطبيق.
6. ربط الشاشات الحالية بالـ RPC المعتمد واختبار الرحلة الكاملة؛ نجاح اختبار SQL وحده لا يعني اكتمال النظام.
7. إعادة تقديم النص الكامل والنسخة الاحتياطية ونتيجة الاستعادة وخطة التراجع للمراجعة قبل أي تطبيق على الإنتاج. لا يتم تجاوز الرفض بتقسيم النص أو استعمال execute_sql.

## خطة التراجع

- قبل الالتزام بالمعاملة: عند خطأ SQL تفشل المعاملة كاملة، ولا تُستخدم خطوات مستقلة تترك نصف سياسات منشورة.
- بعد الالتزام: إيقاف النشر والمهام الجديدة المتأثرة، والرجوع للواجهة السابقة المتوافقة أولًا. لا تحذف جداول أو سجلات جديدة لتقليد التراجع.
- استعادة السياسات والدوال السابقة من النسخة المعتمدة في ترحيل إصلاح مُراجع مع الحفاظ على البيانات الجديدة. لا تُعاد سياسات غير آمنة تلقائيًا.
- الاستعادة الكاملة خيار أخير بعد تقدير الكتابات المفقودة وتسوية المعاملات والإشعارات؛ تُجرّب على نسخة معزولة قبل قرار استعادة الإنتاج.

مرجع النسخ: [Supabase Database Backups](https://supabase.com/docs/guides/platform/backups). النسخ اليومية المُدارة متاحة للخطط المدفوعة المذكورة في الوثائق، ونسخ قاعدة البيانات لا تضم ملفات Storage.
