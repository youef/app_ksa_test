## مخطط قاعدة البيانات الفعلي

### `request_tags`

- الأعمدة: `request_id uuid NOT NULL`، `tag text NOT NULL`.
- FK على `requests(id)` مع `ON DELETE CASCADE`؛ لا حاجة لجدول وسوم مكرر.
- القراءة `TO authenticated USING(true)`؛ الإضافة والحذف تتطلبان أن `requests.requester_id = auth.uid()`؛ لا سياسة UPDATE، ويمكن تنفيذ التعديل عبر استبدال الوسوم بصورة ذرية.
- المفتاح يمنع التكرار الحرفي فقط؛ «بطارية» و« بطارية » أو الاختلافات العربية تبقى مختلفة. CHECK يتحقق طول النص بعد trim لكنه لا يغيّر القيمة المخزنة.
- لا Trigger ولا RPC لهذا النظام في المشروع الحي عند الفحص. عدد السجلات: صفر.

### `borrow_items`

- الأعمدة: `id, owner_id, title, description, category, image_url, city, district, status, max_days, deposit_note, created_at, updated_at`.
- FK للمالك إلى `profiles`؛ لا CHECK على المدة أو الحالة ولا تحديث آلي لـ`updated_at`.
- سياسة «Anyone can read available borrow items» اسمها مضلل؛ شرطها الحقيقي `true` ويعرض جميع الحالات، وليست المتاحة فقط.
- سياسة `ALL` للمالك مع `USING/WITH CHECK auth.uid()=owner_id` تحمي نقل الملكية، لكن لا تفرض قيود النشر أو الموقع أو الحالة.
- فهارس: PK وFK owner فقط؛ لا فهرس مركب للنطاق والحالة والتاريخ.
- عدد السجلات: أداة حقيقية واحدة؛ يجب الحفاظ عليها وعدم استبدالها ببيانات وهمية.

### `borrow_requests`

- الأعمدة: `id, item_id, borrower_id, status, start_date, duration_days, note, created_at, updated_at`.
- FK للغرض والمستعير؛ لا unique جزئي للطلب النشط أو قيود لحالة/مدة؛ لا Trigger أو RPC.
- INSERT يتحقق `borrower_id` فقط، ولا يفحص ملكية الغرض أو توفره أو الحدود الزمنية.
- SELECT للطرفين مناسب مبدئيًا؛ UPDATE للطرفين يشمل كل الحقول بلا آلة انتقال؛ لا يكفي لتفويض القبول للمالك والاستلام/الإرجاع للمشاركين الصحيحين.
- لا حذف مباشر بسياسة؛ يُفضّل الإلغاء المحفوظ بدل حذف تاريخ المعاملة.
- عدد السجلات: صفر.

### `scheduled_broadcasts`

- الأعمدة: `id,title,body,broadcast_type,target jsonb,scheduled_at,status,sent_at,created_by,created_at`.
- قيم موجودة بالكود: `pending, sent, canceled`؛ لا CHECK يلزم هذه القيم ولا Trigger يحميها من الإرسال الوهمي المباشر بواسطة admin.
- فهرس `(status,scheduled_at)` موجود، وFK المنشئ موجود.
- RLS للقراءة والكتابة: `profiles.role='admin'`، وليس أذونات `broadcast` الحالية.
- `admin_send_broadcast`: SECURITY DEFINER، search_path فارغ، يتحقق admin ونصوص وأنواع؛ يستدعي `admin_dispatch_scheduled_broadcast`.
- `admin_dispatch_scheduled_broadcast`: قفل `FOR UPDATE`، يرجع `already_sent` بعد الإرسال، يرفض الحالات الأخرى، ويتحقق بقاء منشئ الحملة admin غير محظور. EXECUTE محصور في authenticated/service_role بعد سحب PUBLIC/anon.
- `app_private.run_backend_job`: محصور في postgres، advisory lock للعمل، يعالج ٢٠ سجلًا مستحقًا مع `FOR UPDATE SKIP LOCKED` في كل تشغيل؛ يُنفّذ pg_cron مهمة `hayna-scheduled-broadcast-dispatch` كل دقيقة من جهة الخادم.
- ثبت نجاح آخر ٤ تشغيلات في `cron.job_run_details` أثناء التدقيق. هذا يثبت تشغيل العامل الفعلي؛ لا يثبت وصول رسالة مجدولة أو Push لأن قائمة الحملات فارغة.
- العامل يستخدم `target.scope` كمدينة أو `all` و`target.segment`؛ لا يدعم حيًا أو انتهاءً أو إعدادات إشعارات عامة. منشئ فقد صلاحيته يظل pending ويُتجاوز باستمرار.
- عدد السجلات: صفر.

### `urgent_alerts`

- الأعمدة: `id,creator_id,title,description,alert_type,city,district,status,location_lat,location_lng,created_at,resolved_at,edit_count`.
- FK للمنشئ؛ لا severity أو expiry أو moderation أو rate limit؛ لا CHECK للحالة أو النوع.
- القراءة العامة `true` لكل الحالات؛ الإضافة لأي authenticated بنفس `creator_id`؛ سياسات تعديل متكررة للمالك/الإدارة، وحذف للمالك/الإدارة. لا منع تغيير الحقول الحساسة كدرجة رسمية مستقبلًا.
- Trigger وحيد لتقييد تعديل النص: `enforce_urgent_alert_edit_limit` يستدعي `enforce_user_listing_edit_limit`؛ لا تطبيق لانتهاء صلاحية أو مراجعة محتوى خاصة بالتنبيه.
- الخريطة تستدعي `select('*').eq('status','active')` وتستخدم `location_lat/location_lng` مباشرة في موضع العلامة. إخفاء العمود بالواجهة وحده لا يصلح التعرض من API.
- عدد السجلات: صفر؛ يمكن إضافة صلاحيات وقيود دون حذف أي محتوى قائم.

## مشاكل مشتركة تتطلب أولوية

1. RLS مفعل في الجداول الخمسة، لكن أدوار `anon` و`authenticated` تملك `TRUNCATE,TRIGGER,REFERENCES` علاوة على CRUD. RLS لا ينطبق على TRUNCATE. قابلية استدعائه مباشرة من Data API تختلف، لكن يجب سحب هذه الامتيازات غير المطلوبة وعدم الاعتماد على سطح API لحماية القاعدة.
2. يوجد مساران نشطان لـPush على INSERT في `notifications`: مسار Vercel وExpo مباشر؛ قد يصل إشعاران للجهاز الأصلي. يوجد كذلك إرسال مباشر من `app/tools.tsx` عبر `lib/pushSender.ts`، ويطلب رموز أجهزة مستلم آخر من العميل. يجب توحيد الإرسال من الخادم دون كشف رموز الأجهزة وتوثيق نتيجة الوصول.
3. تعريف SQL لمسار Push قديم يحتوي سرًا ثابتًا. لم يُنسخ السر إلى هذا التقرير. يجب نقله إلى تخزين أسرار مناسب وتدويره بالتنسيق مع إعداد الخادم، لا تضمينه في migration جديدة.
4. لا يوجد جدول تفضيلات عام للإشعارات في المخطط الذي فُحص؛ الموجود `story_notification_settings` خاص بالقصص. إكمال احترام التفضيلات يحتاج توحيد إعداد حقيقي؛ لا تدّعي الوظيفة أنها تحترم تفضيلًا غير محفوظ.
5. الترحيلات الحالية لا تشمل إنشاء `request_tags`؛ يلزم حفظ مخططه الموجود ضمن baseline قابل لإعادة إنشاء بيئة الاختبار، دون إنشاء جدول مكرر أو مسح البيانات.

- `app/tools.tsx:128`: إنشاء غرض بدون صورة وبقيم موقع افتراضية الرياض/العليا عند غياب ملف المستخدم.

- `supabase/functions/_shared/maintenance.ts` و`scheduled-broadcast-dispatch/index.ts`: غلاف المصادقة الخادمي؛ يجيز admin حاليًا بمقارنة role، ويحتاج التوافق مع RBAC الموحد.

## خطة التحقق قبل تغيير الإنتاج

| النظام | اختبارات ضرورية في بيئة معزولة |
|---|---|
| الوسوم | إنشاء طلب ووسومه ذريًا، تكرار عربي/مسافات، محتوى محظور، حد العدد، غير المالك INSERT/DELETE مرفوض، ظهور البطاقات والتفاصيل والفلتر، رفض الطلب يعيد كل الوسوم |
| الإعارة | إضافة بصورة، نطاق حي/مدينة قبل pagination، طلب ذاتي/مكرر/مدة سالبة أو تتجاوز max_days مرفوض، قبولان متزامنان ينجح أحدهما فقط، لا يستطيع المستعير قبول نفسه، تأكيد الاستلام والإرجاع للطرف الصحيح، إنهاء/إلغاء/رفض، طرف ثالث لا يقرأ الطلب أو المحادثة، إشعار مرة واحدة لكل انتقال |
| الجدولة | مسودة لا ترسل، مستحق يرسل، موعد لاحق لا يرسل، منتهٍ لا يظهر ولا يرسل، مدينة وحي صحيحان، إذن broadcast فقط، فقدان صلاحية المنشئ، فشل قابل لإعادة المحاولة، تشغيل عاملين ويدوي لا يكرر، صورة/رابط آمن، سجل نتيجة بلا أسرار، تفضيلات إشعارات |
| التنبيهات | مستخدم عادي لا ينشر تحذيرًا عامًا رسميًا، حي/مدينة فقط، expiry يوقف القراءة العامة دون انتظار العميل، لا وصول إلى GPS عبر API، حد الإرسال، بلاغ عن تضليل، غير المالك لا يعدّل، انتهاء/إلغاء ومؤشر «تنبيه مجتمعي» واضح |

## تقسيم الملفات المقترح للتنفيذ

- مسؤول أنظمة المجتمع: `lib/requestTags.ts`, `components/requests/RequestTags.tsx`, `app/ask.tsx`, `app/request.tsx`, `app/tools.tsx`, `lib/borrowItems.ts`, `components/community/*`, `app/emergency-alert.tsx`, `components/admin/AdminScheduledBroadcasts.tsx`، وترحيل واحد بعد تنسيق واجهات RPC والأذونات مع المسؤول الرئيسي.
- تنسيق لازم مع المسؤول الرئيسي: دمج مكوّن الوسوم في `TwitterInquiryCard` وفلتر Home، دمج مكوّن الجدولة في `app/admin.tsx`، واجهة صلاحية `broadcast` و`urgent_alerts`، ومراجعة Push المشتركة؛ لا تعديلات متضاربة على ملفات مسؤول السوق والملف الشخصي.
- لا إضافة مسار إعارة أو Broadcast مكرر؛ `/tools` و`/admin` والمسار القديم للتنبيهات تكفي بعد التطوير.
