## 1 — أوقات عمل المتاجر

### الموجود

- جدول `business_hours`: `id uuid`، `business_id uuid NOT NULL`، `day_of_week smallint NOT NULL`، `opens_at time`، `closes_at time`، `is_closed boolean NOT NULL DEFAULT false`، `created_at timestamptz`.
- FK إلى `businesses(id)`، وCHECK لرقم اليوم 0–6. CHECK آخر يفرض إما يومًا مغلقًا بوقتين NULL، أو وقتي فتح وإغلاق مختلفين. يسمح المخطط ضمنيًا بـ`closes_at < opens_at` لكن لا توجد آلية تفسير مثبتة للفترة الليلية.
- UNIQUE على `(business_id,day_of_week)`، وفهرس إضافي مكافئ له في بادئة الأعمدة؛ يجب تقييم إزالة التكرار فقط بعد التحقق، دون تغيير بيانات.
- RLS مفعلة. القراءة لجميع `authenticated`، والكتابة/التعديل/الحذف لمالك المتجر عبر التحقق من `businesses.owner_id`. سياسة UPDATE تحتوي USING وWITH CHECK.
- لا توجد Triggers على `business_hours`، ولا RPC مرتبطة بالساعات، ولا نشر في `supabase_realtime` للجداول الأربعة.

### الناقص والمخاطر

- لا توجد أي قراءة أو كتابة لـ`business_hours` في صفحات التطبيق والخدمات المفحوصة.
- UNIQUE الحالي يمنع دعم فترتين في اليوم. لا توجد أعمدة للمنطقة الزمنية أو إغلاق مؤقت أو أولوية الاستثناء.
- `app/market.tsx` يقرأ `b.is_open` بدل الحقل الفعلي `is_open_now`، ثم يستخدم `true` افتراضيًا؛ ويقرأ `b.working_hours` غير الموجود ويستبدله بنص عام. لذلك حالة «مفتوح» قد تكون افتراضية وليست حسابًا من الساعات.
- صفحة `app/business.tsx` لا تعرض قسمًا لأوقات العمل رغم استيراد Clock.
- قراءة الساعات ليست مقيدة بظهور المتجر واعتماده، كما أنها غير متاحة للضيف وفق السياسة الحالية. يجب توحيدها مع سياسة ظهور المتجر.
- صلاحية المالك الحالية لا تميز أهلية التاجر المحظور/فاقد التوثيق؛ يلزم الاتفاق مع طبقة قدرات السوق الحالية على إمكانية إدارة الساعات، دون منح صلاحيات شاملة.

### الإصلاح المقترح دون جداول أو صفحات مكررة

1. توسيع الجدول نفسه بترتيب الفترة اليومية، ثم استبدال UNIQUE اليوم بقيد ملائم للفترات مع الحفاظ على الصفوف الحالية. منع تداخل الفترات وخلط يوم مغلق بفترات مفتوحة عبر تحقق خادمي واحد.
2. حفظ الإغلاق المؤقت والمنطقة الزمنية ضمن إعدادات المتجر الحالية بعد التأكد من عدم وجود حقول/إعدادات مكافئة؛ الافتراضي السعودي `Asia/Riyadh`.
3. توفير حفظ أسبوع كامل بشكل ذري مع تحقق الملكية والأهلية، بدل حذف ثم إضافة من العميل بما قد يترك أسبوعًا فارغًا عند الانقطاع.
4. حساب مفتوح/مغلق/غير محدد وموعد الفتح القادم من الفترات والتوقيت المحلي، بما يشمل آخر فترة من اليوم السابق عند امتدادها بعد منتصف الليل. لا يصنف جدول غير محدد بأنه «مفتوح».
5. دمج بطاقة الساعات ومحرر المالك في صفحة المتجر وإدارة المنشأة الحالية. إعادة استخدام البطاقة داخل تفاصيل المنشأة بالسوق بعد تنسيق التعديل مع مالك ذلك الملف.

### اختبارات القبول المطلوبة

- قراءة ضيف ومستخدم لمتجر منشور، ورفض ساعات متجر محجوب لغير صاحبه/المخول.
- إضافة وتعديل وحذف المالك، ورفض مستخدم آخر وتغيير `business_id` إلى متجر لا يملكه.
- فترتان باليوم، يوم إجازة، إغلاق مؤقت، نهاية أسبوع، تاريخ بلا ساعات.
- فترة 22:00–02:00 قبل منتصف الليل وبعده، وحدود الثانية عند الفتح والإغلاق.
- رفض التداخل والوقت الناقص والتساوي، وحفظ ذري يتراجع كاملًا عند فشل أي فترة.
- RTL ولوحة مفاتيح الجوال وAndroid/iOS/web، ورسالة قابلة للاسترداد عند انقطاع الاتصال.

## 10 — تقييمات المتاجر والخدمات

### الموجود

- جدول `reviews`: `id`، `reviewer_id`، `business_id`، `service_id`، `rating integer NOT NULL`، `body text nullable`، `created_at`.
- CHECK لنجوم 1–5، وCHECK `review_target` يفرض هدفًا واحدًا فقط: متجر أو خدمة. FKs إلى `profiles` و`businesses` و`services`، وفهارس لأعمدة المرجع الثلاثة.
- RLS: SELECT للضيف والمستخدم بلا قيد، INSERT لمعرف المراجع الحالي فقط. لا توجد سياسة UPDATE أو DELETE، ولا Triggers للمراجعات.
- `app/business.tsx` يحمّل التقييمات، يحسب المتوسط من كامل النتائج، ويتيح إرسال النجوم والتعليق الاختياري.
- `app/user.tsx` يجمع تقييمات متجر صاحب الملف وخدماته لعرض السمعة، بحدود تحميل لكل نوع.
- `business_directory` موجود ويحسب متوسط `rating` و`review_count` من الجدول، وخياره الحي `security_invoker=true` مثبت. يمكن إعادة استخدامه بدل اختراع تجميع مكرر.
- `app_reviews` جدول مستقل لتقييم التطبيق، ولا يجب دمجه أو الخلط بينه وبين `reviews`.

### الناقص والمخاطر

- INSERT يتحقق من هوية المراجع فقط؛ لا يمنع تقييم متجره/خدمته، أو تكرار التقييم لنفس الهدف، أو تقييم هدف غير ظاهر/غير مؤهل. لا يوجد حد طول للتعليق أو مراجعة محتواه مثبتة على جدول reviews.
- لا توجد واجهة إرسال أو قائمة تقييمات في `app/service.tsx`.
- لا توجد آلية تعديل/حذف المراجع وفق سياسة معلنة، ولا إجراء إبلاغ مرتبط بكل تقييم في صفحة المتجر.
- صفحة المتجر تعرض بطاقة مالك النشاط مرتين. أخطاء التحميل تسجّل console فقط وقد تظهر كأن المتجر غير موجود. قائمة المراجعات غير مقسمة إلى دفعات.
- السوق يقرأ حقولًا غير موجودة في `businesses` مثل `rating` و`reviews_count` و`reviews_list` ثم يعرض 5.0 افتراضيًا؛ هذا ليس تقييمًا مثبتًا. التجميع الموجود يستخدم اسم `review_count` بالمفرد.
- تفضيل إشعارات التقييمات ظاهر في صفحة الإشعارات، لكن لا يوجد Trigger أو RPC على reviews لإرسال إشعار بعد تقييم جديد؛ التفضيل وحده لا يثبت الإرسال.

### الإصلاح المقترح

1. توحيد قواعد reviews خادميًا: منع الذات، قيد هدف ظاهر مؤهل، تعليق محدود ومراجع بمسار الاعتدال الموجود، ومنع التكرار بـunique partial indexes لكل `(reviewer_id,business_id)` و`(reviewer_id,service_id)` بعد فحص التعارضات دون حذف بيانات.
2. اعتماد تقييم واحد لكل مستخدم وهدف مع تعديل/حذف صاحبه. منع تغيير reviewer/target بعملية UPDATE، وإتاحة إجراء إدارة مخول ومُسجل عند المخالفة.
3. تحديد أهلية تقييم مناسبة للموجود فعلًا: عند وجود طلب خدمة/عملية مكتملة قابلة للتحقق يمكن ربطها بها. لا تُستخدم عبارة «شراء موثق» ولا تُختلق معاملة عندما لا توجد علاقة فعلية مثبتة.
4. مكوّن موحد للنجوم والإرسال والتعديل والحذف والإبلاغ، يستخدم في المتجر والخدمة، مع pagination وتجميع صحيح للعدد والمتوسط. الحفاظ على صفحة الملف وإصلاح مصادر المجاميع بدل تكرار صفحات.
5. ربط إشعار التقييم بمالك الهدف مع منع الإشعار الذاتي والتكرار واحترام إعدادات الإشعارات. لا يعاد إرسال الإشعار عند إعادة تحميل الواجهة.

### اختبارات القبول المطلوبة

- نجوم 1 و5، ورفض 0 و6 والهدفين معًا/بدونهما، ورفض مراجع مزور.

- محاولة إرسالين متوازيين لنفس الهدف: صف واحد فقط، ورسالة واضحة للمستخدم.
- تعديل/حذف المراجع ورفض شخص آخر، ومنع نقل الهدف أو المراجع.

## 11 — فعاليات الحي

### الموجود

- جدول `events`: معرف ومنظم وعنوان ووصف ومدينة وحي و`starts_at timestamptz NOT NULL` و`ends_at` واسم موقع عام وlatitude/longitude وصورة وحالة نشر واعتماد وتصنيف و`date_label` و`attendees_count` و`is_free` وagenda وguidelines.
- حالات القاعدة الحالية: `published,cancelled,ended`. فهرس `(city,district,starts_at)` وفهرس الاعتماد، وFK المنظم.
- `event_attendees`: `event_id,user_id,status,created_at`، PK مركب يمنع تكرار التسجيل. الحالات `going,interested,cancelled`، وFKs للفعالية والملف الشخصي، وفهرس user_id.
- صفحات العرض والتفاصيل والإضافة مدمجة داخل `app/market.tsx`؛ لا توجد حاجة لصفحة فعالية مستقلة جديدة بمجرد الاستكمال.
- يوجد عرض على الخريطة عبر `lib/mapPins.ts` للمنشور والمعتمد. يوجد اعتماد/رفض للإدارة في `app/admin-pro.tsx`.
- حمايات السوق الأحدث تطبق أهلية المنظم وتستمد المدينة والحي من ملفه خادميًا. Triggers الاعتماد تعيد تغييرات غير المدير إلى pending.
- عمليات RSVP الحالية upsert على PK، والإلغاء delete لصف المستخدم الحالي، مع رسائل نجاح/فشل.

### الأعطال والمخاطر المثبتة

1. **إنشاء الفعالية لا يرسل `starts_at`:** النموذج يحفظ `date_label` نصيًا فقط، بينما starts_at إلزامي بلا default. هذا تعارض مباشر بين الحقول المرسلة والمخطط ويجب إصلاحه بتاريخ حقيقي مع معاينة محلية عربية.
2. **العداد لا يثبت في القاعدة:** الواجهة تزيد/تنقص attendeesCount محليًا. لا توجد Triggers على event_attendees ولا RPC مرتبطة بالحضور، ومهمة refresh-counters الفعلية تحدّث عدادات الملفات فقط. لذلك لا يعتمد العرض على عدد حقيقي مستدام.
3. **الحضور مكشوف:** SELECT على event_attendees متاح لكل مسجل. الواجهة تقصر قائمة الأسماء على المنظم لكنها ليست حماية خادمية.
4. **RSVP بلا أهلية فعالية:** INSERT/UPDATE يتحققان من user_id فقط؛ لا يتحققان من اعتماد/ظهور/إلغاء/انتهاء الفعالية ولا السعة. لا توجد أعمدة للمقاعد أو خصوصية عدد الحضور.
5. استعلام السوق يحمّل آخر 50 فعالية قبل تصفية الموقع محليًا. التصفية تقارن المدينة فقط وتتجاهل نطاق الحي؛ قد تختفي فعاليات مناسبة خلف حد التحميل. لا يستبعد الاستعلام ended/cancelled، كما أن المصفوفة المشتقة تفقد starts_at/ends_at/status فلا تستطيع الواجهة عرض الحالات الزمنية بدقة.
6. لا يوجد CHECK يضمن ends_at بعد starts_at. لا توجد تذكيرات أو وظائف خلفية خاصة بالفعاليات في قائمة Edge Functions/Cron المفحوصة.
7. توجد إحداثيات على events ومتاحة مع SELECT *. يجب أن تمثل موقع فعالية عامًا مصرحًا به فقط، وألا يملأها التطبيق من إحداثيات المستخدم الدقيقة. مسار الخرائط الحالي يستخدم اسم الموقع العام.
8. نص مشاركة الدعوة يقول «الدخول مجاني» دائمًا رغم وجود is_free. ويجب إضافة إجراء بلاغ عن الفعالية إلى مسار reports الموجود بدل إنشاء نظام بلاغات مكرر.
9. اعتماد/رفض الإدارة الحالي تحديث مباشر بلا سجل إجراء مخصص مثبت للفعالية. يتعين ربطه بصلاحيات الإدارة الموحدة والسجل الحساس، ولا يمنح لقب staff صلاحية غير مقصودة.

### الإصلاح المقترح

1. استخراج واجهتي تفاصيل وإنشاء الفعالية من الملف الكبير إلى مكونات مشتركة، مع البقاء في قسم السوق الحالي. حقول تاريخ بداية/نهاية حقيقية وتحويل واضح لتوقيت السعودية، وتحقق خادمي للتواريخ.
2. تصفية المدينة/الحي والحالة الزمنية والاعتماد قبل pagination، والترتيب حسب starts_at. حساب قادمة/جارية/منتهية من الوقت، مع بقاء cancelled حالة صريحة.
3. تضييق قراءة صفوف الحضور إلى صاحب التسجيل والمنظم المخول والإدارة المسموح لها. تقديم عدد مجمع فقط للعامة وفق إعداد الخصوصية، وعدم نشر جدول الحضور كاملًا عبر Realtime.
4. التسجيل والإلغاء في عملية ذرية واحدة تتحقق من ظهور الفعالية وحالتها وسعتها وتستخدم قفلًا يمنع تجاوز آخر مقعد عند التزامن؛ منع تعدد التسجيل بالـPK الموجود. الحفاظ على الحالة cancelled بدل حذف تاريخ التسجيل عند ملاءمة السياسة.
5. إصلاح مصدر العدد في الخادم؛ عند اختيار عداد مخزن، حمايته من تعديل المنظم ومزامنته مع going دون تضخيم بسبب upsert أو status transitions. الحذر من أن تحديث events عبر Trigger الحضور قد يفعّل moderation trigger ويعيد الفعالية إلى pending إن لم يُصمم المسار جيدًا.
6. إضافة سعة اختيارية وإعداد عرض العدد ضمن events الحالي. ربط تذكير آمن ومكرر التنفيذ بلا إرسال مكرر بالجدولة/الإشعارات القائمة بعد اكتمال النظام 13، مع احترام التفضيلات والإلغاء.
7. توحيد الإدارة والبلاغات والمشاركة دون كشف حضور شخصي أو إحداثيات مستخدم.

### اختبارات القبول المطلوبة

- إنشاء منظم مؤهل بتاريخ حقيقي، رفض مستخدم غير مخول أو إحداثيات خاصة مستمدة من ملفه، ورفض تاريخ نهاية سابق للبداية.
- عدم ظهور pending/rejected لغير صاحبها/الإدارة، واحترام حيّي/مدينتي قبل حد الدفعة.
- التسجيل والإلغاء وإعادة التسجيل، وعدم التكرار بعمليتين متوازيتين، ورفض فعالية منتهية/ملغاة/غير مرئية.
- التنافس على مقعد واحد من مستخدمين: قبول واحد فقط، وعدد مطابق بعد إعادة تحميل ومن جهاز آخر.
- رفض قراءة حضور فعالية لغير صاحب السجل/المنظم المخول، ورفض انتحال user_id أو نقل التسجيل لفعالية أخرى دون تحقق.
- عدم إعادة الفعالية المعتمدة إلى pending بسبب تسجيل حضور، وعدم قدرة المنظم على تزوير attendees_count.
- تذكير واحد فقط رغم retry، إيقافه بعد الإلغاء، واحترام تفضيلات المستخدم.
- فلاتر وحالات وفراغ وأخطاء وRTL على web وAndroid/iOS، مع اختبار أن مشاركة الدعوة تعكس السعر الفعلي.

## حزمة التنفيذ المقترحة وتنسيق الملفات

الملفات التالية مقترحات للعمل اللاحق وليست ملفات أضيفت بهذا الفحص:

| المساحة | الملفات المقترحة | الغرض |
| --- | --- | --- |
| ساعات العمل | `lib/businessHours.ts`، `components/business/BusinessHoursCard.tsx`، `components/business/BusinessHoursEditor.tsx`، تعديل `app/business.tsx` | حساب محلي مضبوط وعرض/تعديل ضمن المتجر الحالي. |
| التقييمات | `lib/reviews.ts`، `components/reviews/ReviewSection.tsx`، تعديل `app/business.tsx` و`app/service.tsx` و`app/user.tsx` | API موحد ومكوّن مشترك ونتائج مجمعة صحيحة. |
| الفعاليات | `hooks/useEvents.ts`، `components/events/EventComposer.tsx`، `components/events/EventDetails.tsx`، دمج محدود متفق عليه في `app/market.tsx`، وتعديل `lib/mapPins.ts` | إصلاح النموذج والتاريخ والنطاق والحضور دون تكرار صفحة. |
| قاعدة البيانات | migrations جديدة مولّدة عبر `supabase migration new`، واختبارات SQL أدوار في بيئة منفصلة | تعديل الجداول والسياسات الموجودة، دون DDL إنتاجي قبل نجاح الاختبارات. |
| الاختبارات | وحدات حساب ساعات وحالات فعاليات؛ تكامل SQL للملكية والذات والتكرار والمقاعد والخصوصية | تثبيت السلوك الفعلي، ثم smoke tests للواجهات والبناء. |

قبل التنفيذ: baseline للمخطط + بيئة معزولة + بيانات اختبار مميزة لا تصل للإنتاج، ثم migrations قابلة للتتبع، واختبارات قبول، ثم PR ومعاينة. لا تُغير صور الخلفيات أو نظام التنقل، ولا تُعدل ملفات السوق/إدارة المنشأة المتزامنة مع عمل زميل إلا بتنسيق ملكية واضح.
